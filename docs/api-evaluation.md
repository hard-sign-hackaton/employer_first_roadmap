# Проверка API для оценки

## Что уже есть

- [`openapi.json`](../openapi.json) — OpenAPI 3.1, все 49 маршрутов из `employerapi/handler.go`, схемы запросов и ответов, Bearer-аутентификация и роли.
- [`DATA-API.yaml`](../DATA-API.yaml) — последовательность обязательных проверок с методами, путями, параметрами, ролями, ожидаемыми статусами и полями ответа.
- [`api-test-data.json`](api-test-data.json) — воспроизводимые тестовые значения. Маркеры `<...>` заменяются ID из ответов API; `<run-id>` — уникальный суффикс запуска.

## Адрес API

Публичный базовый адрес в файлах проверки — `https://135.106.216.99` (стандартный порт 443). После выпуска сертификата перед передачей жюри следует проверить `GET /healthz` извне с обычной проверкой TLS и убедиться, что сертификат действителен весь период оценки. Если HTTPS будет настроен на другом порту, адрес в `DATA-API.yaml` и `openapi.json` надо синхронно изменить.

Платформа оценки не предоставила формальную схему и номер версии `DATA-API.yaml`. Текущий `schema_version: "1.0"` — версия нашего манифеста. Если организаторы передадут официальный шаблон, файл потребуется привести к нему.

## Тестовые учётные записи

| Роль | Логин | Как получить токен |
| --- | --- | --- |
| admin | `bootstrap-admin` | Защищённый канал передачи значения `ADMIN_API_TOKEN`, заданного на сервере. Админ нужен только для создания тестовой компании и аккаунта работодателя. |
| employer | `efr-evaluator-<run-id>` | `POST /api/v1/admin/accounts` после создания компании; ответ содержит `token` только один раз. |

Токены — эквивалент паролей: их нет в репозитории, OpenAPI, фикстурах или PDF. Жюри надо передать их отдельно по защищённому каналу. Для API парольная форма входа не предусмотрена; используются Bearer-токены. Бот MAX — отдельная роль пользователя и не имеет API-токена. Для сквозной проверки `/feedback` нужна реальная тестовая заявка, созданная прохождением сценария в боте.

## Порядок воспроизведения

1. Проверить `GET https://135.106.216.99/healthz` и валидность сертификата.
2. С админ-токеном вызвать `GET /api/v1/me`, `GET /api/v1/reference-data` и сохранить ID первого региона и интереса. Создать тестовый вуз и программу через admin API; затем проверить `GET /api/v1/education-programs`.
3. Создать тестовую компанию через `POST /api/v1/admin/companies` с `company` из JSON, заменив `<run-id>` на уникальный суффикс.
4. Создать аккаунт работодателя через `POST /api/v1/admin/accounts`, подставив ID компании. Сохранить возвращённый токен локально, не коммитить.
5. С токеном работодателя обновить профиль, создать направление, привязать программу и интерес, создать неактивную возможность. Проверить GET-списки и изоляцию ролей.
6. Для положительной проверки feedback создать настоящую заявку в боте: дойти до этапа стажировки или практики и нажать «Я отправил заявку», затем взять `application_id` (ID отдельной попытки, **не** `roadmap_id`) из `GET /api/v1/employer/applications`, отправить `PATCH /api/v1/employer/applications/{applicationID}` с `feedback` из JSON и повторить GET. Ожидается новый статус и запись в `feedback_history`; бот попытается уведомить пользователя сразу, а ответ останется доступным через `/feedback`.
7. Деактивировать аккаунт работодателя и архивировать тестовые компанию, программу и вуз. Эти операции есть в конце `DATA-API.yaml`; выполнять их и при прерывании проверки.

В `DATA-API.yaml` автоматизированные проверки feedback покрывают отказ для неизвестной заявки (`404`). Положительный сценарий зависит от события в MAX и не может быть достоверно создан одними текущими REST-методами; его проверяют шагом 6.

## Локальная валидация контракта

```powershell
python tools/generate_openapi.py
python -m json.tool openapi.json > $null
python -m json.tool docs/api-test-data.json > $null
```

Генератор остановится с ошибкой, если число/пути операций перестанут совпадать с регистрацией маршрутов в Go. Для локальной проверки приложения: `docker compose up --build -d` и `docker compose -f docker-compose.yml -f docker-compose.test.yml run --rm efr_bot go test ./...` (Docker должен быть запущен).
