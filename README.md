# Employer First Roadmap

## Назначение решения

Employer First Roadmap — бот в MAX, который строит школьнику или абитуриенту
путь от выбора работодателя и карьерного направления до ЕГЭ, поступления,
практики/стажировки и заявки работодателю.

Работодатель управляет своей компанией, направлениями и возможностями через
REST API. Бот не использует отдельные моковые ответы: пользовательский сценарий
читает тот же каталог PostgreSQL, который заполняют администратор и
работодатель. После подтверждения заявки на возможность работодателя она
появляется в API. Работодатель оставляет статус, сообщение и контакт; бот
пытается сразу уведомить пользователя, а вся история доступна по `/feedback`.

## Основной пользовательский сценарий

1. Администратор создаёт компанию и API-аккаунт работодателя.
2. Администратор ведёт общие данные: вузы, образовательные программы, наборы
   ЕГЭ, проходные баллы, правила приёма и шаблоны roadmap.
3. Работодатель по своему Bearer-токену заполняет профиль компании, карьерные
   направления, связи с образовательными программами и возможности: практики,
   стажировки, проекты и целевое обучение.
4. Пользователь открывает бота в MAX, отправляет `/start`, указывает класс,
   регион, интересы и предметы, затем выбирает компанию и направление.
5. Бот формирует roadmap на основании данных из PostgreSQL. Текущий путь можно
   продолжить командой `/roadmap`.
6. На этапе стажировки или практики пользователь переходит по ссылке
   работодателя, подаёт заявку и нажимает в боте «Я отправил заявку». Это не
   завершает сам этап: его окончание подтверждается отдельно. На финальном
   шаге roadmap можно также подтвердить заявку в компанию.
7. Работодатель получает заявку через `GET /api/v1/employer/applications` и
   отвечает через `PATCH /api/v1/employer/applications/{applicationID}`.
8. После ответа работодателя бот пытается отправить уведомление в MAX.
   Пользователь может отправить `/feedback` и увидеть актуальный статус,
   сообщение, контакт и историю изменений независимо от доставки уведомления.

Важно: `/feedback` до подтверждения любой заявки корректно сообщает, что
заявок пока нет. Сам бот не отправляет анкету на внешний сайт работодателя —
пользователь делает это по предоставленной ссылке и подтверждает действие.

## Состав и архитектура

Локальное решение состоит из двух Docker-сервисов:

- `efr_bot` — один Go-процесс с обработчиками MAX, планировщиком напоминаний и
  REST API работодателя/администратора;
- `postgres` — PostgreSQL 16, в которой находятся каталог, профили
  пользователей, roadmap, заявки и история обратной связи.

Поток данных:

```text
Администратор / работодатель -> REST API -> GORM -> PostgreSQL
                                                   |
Пользователь MAX <- обработчики бота <- сервисы <--+
                                                   |
Работодатель <- заявки / отправляет feedback ------+
```

Основные каталоги проекта:

- `employerapi/` — HTTP-маршруты, Bearer-аутентификация, роли `admin` и
  `employer`;
- `handlers/` — диалоги и команды бота;
- `services/` — бизнес-логика профиля, траектории, поступления и roadmap;
- `repositories/` — доступ к данным через GORM;
- `models/` — модели PostgreSQL;
- `database/` — подключение, автомиграции, обязательные справочники и seed;
- `reminders/` — еженедельные и тестовые напоминания;
- `integration/` — сквозные интеграционные тесты.

## Быстрый запуск всех локальных компонентов

Требуются Docker Desktop с Docker Compose и действующий токен бота MAX.
Скопируйте `.env.example` в `.env`, заполните как минимум `BOT_TOKEN` и
`ADMIN_API_TOKEN`, затем из корня проекта выполните **одну команду**:

```bash
docker compose up --build -d
```

Команда поднимает PostgreSQL и приложение с API на `http://localhost:8080`.
Обычный контур создаёт схему и обязательные справочники, но оставляет каталог
компаний пустым: его заполняют администратор и работодатели через API.

Проверка запуска:

```bash
docker compose ps
curl http://localhost:8080/healthz
docker compose logs -f efr_bot
```

Ожидаемый healthcheck:

```json
{"status":"ok"}
```

## Параметры и переменные окружения

Файл `.env` размещается рядом с `docker-compose.yml`. Секреты не следует
коммитить; `.env` уже добавлен в `.gitignore`.

| Переменная | Обязательность | Значение по умолчанию | Назначение |
| --- | --- | --- | --- |

| `ADMIN_API_TOKEN` | обязательна для управления каталогом | пусто | Bootstrap-токен администратора; при старте создаётся/обновляется аккаунт `bootstrap-admin`. |
| `EMPLOYER_API_PORT` | нет | `8080` | Порт REST API на хосте и внутри контейнера. |
| `EMPLOYER_ALLOWED_ORIGIN` | только для браузерного кабинета | пусто | Точный CORS origin, например `http://localhost:3000`. |
| `REMINDERS_ENABLED` | нет | `true` | Включить еженедельные напоминания. |
| `REMINDER_CRON` | нет | `0 10 * * 1` | Cron из пяти полей; по умолчанию понедельник, 10:00. |
| `REMINDER_TIMEZONE` | нет | `Europe/Moscow` | IANA-таймзона расписания. |
| `POSTGRES_DB` | нет | `employer_first_roadmap` | Имя локальной БД в Compose. |
| `POSTGRES_USER` | нет | `efr` | Пользователь PostgreSQL. |
| `POSTGRES_PASSWORD` | рекомендуется изменить | `efr_local_password` | Пароль PostgreSQL. |
| `APP_ENV` | нет | `development` | Значение `demo` включает demo-seed. |
| `SEED_DEMO_DATA` | нет | `false` | Явно включает тестовый каталог. |
| `SEED_MAIN_CATALOG` | нет | `false` | Включает основной каталог. |
| `DB_HOST`, `DB_PORT`, `DB_NAME` | только вне Compose | `localhost`, `5432`, `employer_first_roadmap` | Прямое подключение Go-приложения к PostgreSQL. |
| `DB_USER`, `DB_PASSWORD`, `DB_SSLMODE` | только вне Compose | `efr`, `efr_local_password`, `disable` | Учётные данные и SSL-режим прямого подключения. |

Минимальный пример:

```env
BOT_TOKEN="ваш_токен_MAX"
ADMIN_API_TOKEN="длинный_случайный_секрет"
EMPLOYER_API_PORT=8080
EMPLOYER_ALLOWED_ORIGIN="http://localhost:3000"
```

## API работодателя и администратора

Машиночитаемый контракт — [`openapi.json`](openapi.json), манифест проверок —
[`DATA-API.yaml`](DATA-API.yaml), фикстуры и порядок оценки —
[`docs/api-evaluation.md`](docs/api-evaluation.md). Для публичной проверки в
контракте указан `https://135.106.216.99`; локальный адрес остаётся HTTP.
В OpenAPI для запросов и ответов приведены реалистичные примеры JSON; это
иллюстрации для Swagger, а не автоматически созданные записи БД. ID в примерах
нужно заменять на ID, полученные из API.

Базовый URL локально: `http://localhost:8080`. Кроме `GET /healthz`, все ручки
требуют заголовок `Authorization: Bearer <token>`. В БД сохраняется только
SHA-256-хэш API-токена. Роль администратора имеет bootstrap-токен из
`ADMIN_API_TOKEN`; отдельный токен работодателя возвращается только при создании
аккаунта или его перевыпуске.

Общие ручки:

| Метод и путь | Назначение |
| --- | --- |
| `GET /healthz` | Проверка процесса без авторизации. |
| `GET /api/v1/me` | Текущий API-аккаунт и роль. |
| `GET /api/v1/reference-data` | Регионы, интересы и предметы ЕГЭ. |
| `GET /api/v1/education-programs` | Все внесённые образовательные программы, включая архивные. |

Кабинет работодателя; компания всегда определяется токеном, а не ID в URL:

| Метод и путь | Назначение |
| --- | --- |
| `GET`, `PUT /api/v1/employer/company` | Просмотреть или изменить свою компанию. |
| `GET`, `POST /api/v1/employer/directions` | Список или создание своих направлений. |
| `PATCH /api/v1/employer/directions/{directionID}` | Изменить своё направление. |
| `PUT /api/v1/employer/directions/{directionID}/education-programs` | Заменить связи направления с ОП. |
| `PUT /api/v1/employer/directions/{directionID}/interest-tags` | Заменить интересы и их веса. |
| `GET`, `POST /api/v1/employer/opportunities` | Список или создание возможностей. |
| `PATCH /api/v1/employer/opportunities/{opportunityID}` | Изменить или деактивировать возможность. |
| `GET /api/v1/employer/applications` | Заявки только своей компании. |
| `PATCH /api/v1/employer/applications/{applicationID}` | Добавить статус, сообщение и контакт в историю заявки. |

Backoffice администратора находится под `/api/v1/admin/*`:

| Ресурс | Доступные операции |
| --- | --- |
| `/accounts` | `GET`, `POST`, `PATCH /{accountID}`, `POST /{accountID}/rotate-token`. |
| `/companies` | `GET`, `POST`, `PUT /{companyID}`, `PATCH /{companyID}/archive`. |
| `/companies/{companyID}/directions` | `POST`, изменение/архивация направления, привязка ОП и интересов. |
| `/companies/{companyID}/opportunities` | `POST`, изменение и архивация возможности. |
| `/universities` | `GET`, `POST`, `PUT /{universityID}`, `PATCH /{universityID}/archive`. |
| `/education-programs` | `GET`, `POST`, `PUT /{programID}`, `PATCH /{programID}/archive`. |
| `/exam-combinations` | `GET`, `POST`, `PUT /{combinationID}`. |
| `/admission-scores` | `GET`, `PUT`. |
| `/admission-rules` | `GET`, `PUT`. |
| `/roadmap-templates` | `GET`, `POST`. |

Вместо удаления основных сущностей используются archive-ручки. Архивные записи
не участвуют в новых рекомендациях, но остаются доступными для истории уже
созданных roadmap.

Пример ответа работодателя:

```http
PATCH /api/v1/employer/applications/123 HTTP/1.1
Host: localhost:8080
Authorization: Bearer <employer-token>
Content-Type: application/json

{
  "status": "interview",
  "message": "Приглашаем на интервью во вторник в 15:00",
  "contact": "hr@example.com"
}
```

Допустимые статусы: `under_review`, `interview`, `accepted`, `rejected`.
Изменение создаёт новую запись истории, а не стирает предыдущую.

## Работа с данными

- При каждом старте GORM выполняет безопасную `AutoMigrate` и идемпотентно
  заполняет обязательные справочники регионов, интересов и предметов ЕГЭ.
- В базовом контуре компании, направления, вузы, ОП и возможности не
  создаются автоматически.
- Каталог работодателя, пользовательские профили, roadmap, заявки, feedback и
  журнал напоминаний хранятся в PostgreSQL.
- Данные PostgreSQL сохраняются в именованном Docker volume `postgres_data` и
  переживают `docker compose down` и повторный запуск.
- API-токены хранятся в виде SHA-256-хэшей. `BOT_TOKEN`, исходный
  `ADMIN_API_TOKEN` и пароль БД остаются переменными окружения.
- Временное состояние текущего диалога хранится в памяти процесса. После
  рестарта бота сохранённые данные и roadmap остаются в БД, но пользователю
  может понадобиться отправить `/start` или `/roadmap` для продолжения.

## Тестовые данные

Demo-контур изолирован отдельным именем проекта, именем БД и volume:

```bash
docker compose -p efr_demo -f docker-compose.yml -f docker-compose.demo.yml up --build -d
```

Он содержит связный тестовый каталог для прохождения всех веток. Это данные в
той же PostgreSQL и через те же репозитории, а не отдельные заглушки в боте, но
они предназначены только для разработки и демонстрации. Названия организаций и
вузов могут быть реальными, а связи, баллы и возможности являются тестовыми.

Остановка с сохранением тестовых данных:

```bash
docker compose -p efr_demo -f docker-compose.yml -f docker-compose.demo.yml down
```

Полный сброс только demo-БД:

```bash
docker compose -p efr_demo -f docker-compose.yml -f docker-compose.demo.yml down -v
```

Основной контур использует отдельный каталог с официальными ссылками:

```bash
docker compose -p efr_main -f docker-compose.yml -f docker-compose.main.yml up --build -d
```

Он использует БД `employer_first_roadmap_main` и volume
`postgres_main_data`; demo-seed в этом контуре выключен.

## Пошаговый сценарий проверки

1. Создайте `.env`, заполните `BOT_TOKEN` и `ADMIN_API_TOKEN`.
2. Для быстрой сквозной проверки запустите demo-контур командой из раздела
   «Тестовые данные».
3. Убедитесь, что `curl http://localhost:8080/healthz` возвращает
   `{"status":"ok"}`.
4. С токеном администратора вызовите `GET /api/v1/admin/companies`, выберите
   `id` компании и создайте для неё работодателя:

   ```http
   POST /api/v1/admin/accounts
   Authorization: Bearer <ADMIN_API_TOKEN>
   Content-Type: application/json

   {"login":"demo-employer","role":"employer","company_id":1}
   ```

   Сохраните `token` из ответа: повторно прочитать его через GET нельзя.
5. Проверьте `GET /api/v1/me`, `GET /api/v1/employer/company`, направления и
   возможности с новым токеном работодателя.
6. В MAX отправьте боту `/start`, пройдите опрос и выберите компанию и
   направление из каталога. Если диалог надо начать заново, используйте
   `/restart`; если надо вернуться к созданному пути — `/roadmap`.
7. Последовательно подтверждайте этапы roadmap. На этапе стажировки или
   практики откройте ссылку работодателя и нажмите «Я отправил заявку» после
   отправки формы. Затем отдельно отметьте завершение этого этапа.
8. Получите `application_id` через
   `GET /api/v1/employer/applications` и отправьте feedback через PATCH из
   примера выше.
9. После ответа работодателя проверьте уведомление в MAX и отправьте
   `/feedback`. Команда должна показать компанию, возможность, русский текст
   статуса, сообщение, контакт и, после повторных изменений, историю статусов.
   Если уведомление не доставилось, сохранённый ответ остаётся доступен через
   `/feedback`.
10. Проверьте автоматические тесты в отдельной БД:

    ```bash
    docker compose -p efr_test -f docker-compose.yml -f docker-compose.test.yml up -d --wait postgres
    docker compose -p efr_test -f docker-compose.yml -f docker-compose.test.yml run --rm --no-deps tests
    docker compose -p efr_test -f docker-compose.yml -f docker-compose.test.yml down -v
    ```

Тесты не подключаются к MAX. Они проверяют сервисы, GORM, PostgreSQL, роли API,
напоминания и сквозной путь «каталог → профиль → направление → ЕГЭ → roadmap».

## Примеры ожидаемого поведения

- Пустой базовый каталог: бот сообщает «Каталог работодателей пока пуст» и не
  показывает выдуманные компании.
- Выбор `10 класс`: бот принимает нажатие кнопки как выбранный класс и
  продолжает опрос; ввод номера класса вручную не требуется.
- `/roadmap` без активного пути: бот сообщает, что сначала надо пройти опрос.
- `/feedback` до заявки: бот сообщает, что заявка появится после отметки
  «Я отправил заявку» на возможности работодателя.
- PATCH feedback с токеном другой компании: API не раскрывает чужую заявку и
  возвращает ошибку доступа/отсутствия ресурса.
- `/feedback` после ответа работодателя: пользователь видит, например,
  «приглашение на интервью», сообщение и контакт.
- Перезапуск Compose без `-v`: каталог, roadmap, заявки и feedback сохраняются.

## Зависимости и внешние интеграции

Основные зависимости:

- Docker Desktop и Docker Compose;
- Go `1.26.5` для локальной разработки;
- PostgreSQL `16-alpine`;
- GORM `1.31.2` и PostgreSQL-драйвер GORM `1.6.3`;
- MAX bot SDK (`maxbot` и `max-bot-api-client-go/v2`);
- `robfig/cron/v3` для напоминаний;
- `godotenv` для локального `.env`.

Внешние сервисы и интеграции:

- MAX Bot API — сообщения, кнопки, callback-события и напоминания;
- Docker Hub — получение базовых образов Go, Alpine и PostgreSQL при первой
  сборке;
- `gu-st.ru` — загрузка российских доверенных корневых сертификатов во время
  сборки Docker-образа;
- сайты работодателей и вузов — в БД хранятся ссылки, автоматической отправки
  заявок или синхронизации с этими сайтами нет.

## Известные ограничения

- Графического кабинета работодателя нет: доступен REST API.
- Первичное наполнение вузов, ОП, экзаменационных комбинаций и правил приёма
  выполняет администратор; работодатель связывает свои направления с готовыми
  образовательными программами.
- Заявка на внешнем сайте работодателя не проверяется автоматически; бот
  доверяет нажатию «Я отправил заявку».
- Уведомление о новом ответе работодателя отправляется через MAX в режиме
  best-effort: сбой доставки не отменяет сохранение feedback. Команда
  `/feedback` позволяет проверить ответ и историю в любой момент.
- Диалоговое состояние хранится в памяти одного процесса; горизонтальное
  масштабирование без общего state storage не поддержано.
- Автомиграции удобны для MVP, но не заменяют версионированные production
  migrations и процедуру backup/restore.
- Локальные значения пароля PostgreSQL небезопасны для production. HTTPS и
  внешний reverse proxy в Compose не настроены.
- Доступность MAX, Docker Hub и `gu-st.ru` влияет соответственно на работу
  бота и первую сборку образа.

## Остановка и повторный запуск

Остановить приложение, сохранив данные:

```bash
docker compose down
```

Повторно запустить с пересборкой:

```bash
docker compose up --build -d
```

Посмотреть состояние и логи:

```bash
docker compose ps
docker compose logs -f efr_bot
```

Полностью удалить локальную БД и начать с чистого состояния:

```bash
docker compose down -v
```

Последняя команда необратимо удаляет volume текущего Compose-проекта. Для
demo-, main- и test-контуров всегда указывайте те же `-p` и `-f`, что были
использованы при запуске, чтобы не удалить данные другого контура.
